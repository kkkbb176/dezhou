# 不确定修复处理规则 —— 规范文本

> **本文件是规范文本**（一手证据，`PRIMARY`）。它规定**在无法确认根因、依据不足或结果自相矛盾时
> 本项目的强制行为**，并给出必须使用的报告格式。
>
> 生效范围：所有 Bug 审计、功能修复与策略模型开发。
>
> 它**不产生任何数值参数**；数值一律由代码产出（见 `docs/KNOWLEDGE_POLICY.md` 第 1 节
> 「Math Truth 永不被覆盖」）。

---

## 0. 核心原则

> **宁可明确报告「模型暂时无法评估某个动作」，也不要给出看似精确、实际上缺少计算依据的决策。**

项目的目标是**中低级别现金局的实用 Exploit 决策软件**，
不是为通过测试而不断堆叠未经验证的规则。

---

## 1. 触发条件（出现任一即适用本规范）

| 触发 | 说明 |
|---|---|
| 根因无法确认 | 观察到异常，但无法用证据把原因收敛到一处 |
| 数学公式不完整 | 公式缺少分支、缺少分母、量纲不一致或边界未定义 |
| 扑克策略依据不足 | 需要一条「牌桌上应该这么打」的判断，但没有模型或数据支撑 |
| 测试结果相互矛盾 | 两个都「有依据」的断言/输出互相打架 |
| 需要新增模型假设 | 必须引入一条新的先验、阈值或条件概率才能继续 |

---

## 2. 八条强制规则

1. **不得为了让测试通过而调整策略参数、硬编码最终动作或放宽断言。**
2. **必须明确区分四种结论**：
   `CONFIRMED_BUG` / `MODEL_LIMITATION` / `NOT_IMPLEMENTED` / `INCONCLUSIVE`。
   不得用「已修复」笼统覆盖其中任何一种。
3. **优先使用四类取证手段**：最小复现牌局、独立数学计算、源码调用链追踪、单变量对照实验。
4. **只修改根因已确认、修复效果可验证的部分。**
   对存在多种合理实现方案**且会改变扑克策略**的部分，**不得擅自选择**。
5. **无法确认正确实现时停止该项修改**，保留现有代码，报告：阻塞原因、可复现证据、候选方案及各自影响。
6. **若问题会导致软件输出缺乏依据的高风险动作，必须显式标记该动作尚未得到模型支持**，
   不得把它伪装成已证明的最优策略。
7. **不得因为一个新问题，删除或破坏已通过验证的**翻前范围、牌力计算、人物画像、
   下注响应或 EV 模块。
8. **部分成功必须分开报告**：已验证的改动与尚未解决的部分分别列出，
   **不得笼统宣布整个功能 PASS**。

---

## 3. 四种结论的定义（判定口径）

| 结论 | 定义 | 必须附带的证据 | 允许的动作 |
|---|---|---|---|
| `CONFIRMED_BUG` | 根因唯一、可复现、且与既有规范/数学冲突 | 最小复现 + 逐位可复现的数字 + 受影响函数 | 可以修，且必须附回归测试 |
| `MODEL_LIMITATION` | 计算链路正确，但模型假设本身不完备或未校准 | 显示「同一假设不同取值 ⇒ 结论如何变化」的敏感性数据 | 只能**标注与披露**；改假设前需要数据或人工裁决 |
| `NOT_IMPLEMENTED` | 该条件范围 / 概率 / EV 根本不存在 | 代码中显式的 `NOT_IMPLEMENTED` 或缺失字段 + 未评估清单 | 只能**如实披露**；不得用别的量顶替 |
| `INCONCLUSIVE` | 证据不足以在这几者之间判定 | 已排除的候选 + 仍未排除的候选 | **停止**，按第 5 条报告并交人工裁决 |

---

## 4. 强制报告格式

任何一次审计/修复的最终报告**必须**包含以下九行（缺失即视为报告不合格）：

```text
问题是什么：
已确认的根因：
实际复现证据：
已经验证的修复：
仍然不确定的部分：
是否改变了原有策略：
是否存在回归风险：
建议下一步：
是否需要人工裁决：
```

约定：
- 「实际复现证据」必须是**可重跑的**（脚本路径 + 原始输出文件），不是转述；
- 「已经验证的修复」必须给出**锁定该修复的测试**；
- 「是否改变了原有策略」必须逐条列出**行为变化**（哪个节点、从什么动作变成什么动作）；
- 「是否需要人工裁决」在出现「多种合理实现且会改变策略」时**必须为「是」**，
  并列出候选方案与各自影响。

## 5. 与本项目既有规范的关系

| 既有规范 | 关系 |
|---|---|
| `docs/KNOWLEDGE_POLICY.md` 第 1 节 | 本规范**不覆盖**优先级链；相反，第 2.4 条（只改已确认根因）与「Math Truth 永不被覆盖」是同一条纪律的两个侧面 |
| 规范「算不了就说算不了」 | 本规范第 2.6 条是它在**输出层**的延伸：算不了不仅要返回「算不了」，还要在**动作层**标注「该动作未获模型支持」 |
| 规范「禁止两个生产入口」 | 本规范第 2.7 条禁止为了修补一处而破坏已验证模块 |

### 本规范的**三次**实际生效记录

0. **审计轮 · 规则 5/6 生效（发现 P0 后立即停止扩大扫描）**：轻量审计在跑到第 5 个深度节点时
   命中 P0，随即**停止**20–30 节点的全量扫描，改为提交「最小复现 + 独立复算 + 根因 + 影响面 +
   建议最小修复」，且**未自行修改产品代码**。

1. **U1 轮 · 规则 1/2/4 生效**：`test/raiseResponseU1.test.ts` 的 U1-2 最初断言
   「加注越大 ⇒ P(跟) 单调下降」，**跑到第 2 步就失败**（0.36097 → 0.36744）。
   此时**没有**改断言去凑绿，也**没有**调参去凑断言，而是先取证
   （`scripts/u1-response-monotonicity.ts`：6 个节点 / 29 个尺寸点），
   结论是「**断言写错了模型声称的性质**」：模型只声称「继续率单调下降」，
   而 `P(跟) = 1 − P(弃) − P(再加注)` 在两项同时下降时可以上升。
   于是 U1-2 改锁**数学确定**的三条单调性，另立 U1-2b 作为**已知局限的变更探测器**
   （锯齿消失会故意变红，强制回来更新登记表 U9）。
2. **U1 轮 · 规则 8 生效**：加注 EV 已实现，但**不**宣告整体 PASS ——
   系数未校准、再加注分支取下界、方案①/② 名次分歧三项全部保留在登记表，
   并在报告里单独列出「未做全节点扫描」这一证据缺口。
3. **P0 修复轮 · 规则 2/3/7 生效**：修复**只动**已确认根因（资金口径 + 赔率 + 静默关闭），
   **没有**为了让 AK 选 CALL / 99 选 RAISE / F-01 恢复旧动作而调整任何策略系数 ——
   F-01 的动作变化是口径修正的**结果**，且差距落在容差带内，报告里如实标为**边缘决策**。
   同时按规则 7 把「原断言为何无效」写清楚后再替换（`test/raiseResponseU1.test.ts` 的 U1-7
   曾复刻错误公式），并新增**独立手算**的现金流不变量测试（`test/raiseEvCashflowP0.test.ts`）。
