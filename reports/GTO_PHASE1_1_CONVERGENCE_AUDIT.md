# GTO Phase 1.1 —— 收敛与质量审计

> 本报告回答三个问题：
> 1. **同一场景重新求解会不会漂移？**（实测）
> 2. **「求解器返回了数据」与「数据能用」差在哪里？**（质量等级规则）
> 3. **能不能用一个统一的 BR-gap 阈值判断好坏？**（**不能**，附实测依据）

---

## 0. 结论

| 项 | 结果 |
|---|---|
| 重复求解稳定性 | ✅ **逐位一致**（4/6/9MAX 各 2 次独立求解，最大绝对差 **0.0000**） |
| 稳定性阈值依据 | ✅ 实测（0）的 100 倍余量 → `0.01` |
| 是否有统一的质量判定 | ✅ 7 档质量等级（**质量 ≠ API 成功**） |
| 是否用跨桌型固定 gap 阈值 | ❌ **没有**（实测证明不同树的 gap 差 60 倍） |
| 近似模型是否封顶 | ✅ 天花板 = `APPROXIMATE`（GTOpen 翻前是近似延续模型） |
| 低质量是否可能显示成高质量 | ❌ 不可能（迭代过少 / 未达标 / 无稳定性证据 / 漂移大 都会降级） |

## 1. 重复求解稳定性（用户 §六）

### 1.1 方法

对每个场景：**重新建树 + 从迭代 0 求解**，各做 2 次（每次都用全新的 Provider，
不共享会话指纹、不共享内存缓存）。比对：动作菜单、169 类频率、
场景哈希、收敛指标、BR gap。

用「最大/平均绝对差」而不是逐 bit 相等 —— 浮点求和在并行程序里不保证逐 bit 一致。
比较方式是把每张表的动作按 `kind@size` 归一成映射再比，
**A 有而 B 没有的动作按频率 0 处理**（最严格的比法）。

### 1.2 实测结果（`reports/evidence/gto-stability-evidence.txt`）

| 桌人数 | Hero | 迭代 | 菜单一致 | **最大绝对差** | **平均绝对差** | 差 >1% 的条目 | gap A → gap B | 耗时 |
|---|---|---|---|---:|---:|---:|---|---|
| 4 | CO | 60 | ✅ | **0.0000** | 0.00000 | 0 | 0.03412694 → 0.03412694 | 3.1s / 3.9s |
| 6 | UTG | 40 | ✅ | **0.0000** | 0.00000 | 0 | 0.16526006 → 0.16526006 | 53.1s / 46.7s |
| 9 | UTG | 12 | ✅ | **0.0000** | 0.00000 | 0 | 0.02102956 → 0.02102956 | 161.7s / 161.2s |

**三次都是逐位一致** —— 不仅是「统计上接近」，而是 169 类里
**没有任何一类的任何动作频率差异超过 1%**，BR gap 连小数点后 8 位都相同。

### 1.3 这说明了什么、又不说明什么

**说明**：GTOpen 的翻前求解在实践中是**确定性**的。这与源码实现相符
（DCFR + 固定种子、`coupled_deck_v1` 的 1024 个确定性潜在强度样本、seed 90210）。

**不说明**：
- 不能推出「换机器 / 换线程数也逐位一致」（并行归约顺序可能不同）
- 不能推出「升级求解器版本后仍一致」
- **更不能**推出「这份策略是对的」—— 确定性只说明「重复得到同一个答案」，
  不说明那个答案接近真实扑克（见 §4）

### 1.4 阈值怎么定的（**不允许拍脑袋**）

```
实测最坏最大绝对差 = 0.0000
        ↓
选择 GTO_STABILITY_MAX_ABS_DELTA = 0.01
        ↓
理由：实测 0 的 100 倍余量
  · 宽松到不会把「浮点求和顺序差异」误判为不稳定
  · 严格到能抓住任何**有决策意义**的漂移（1 个百分点的频率差足以改变边缘决策）
```

⚠️ 阈值调宽必须同时更新本节与 `gtoQuality.ts` 的注释 ——
不允许为了「让结果显得稳定」而把阈值改到比实测漂移还松。

### 1.5 稳定性证据如何进入质量评级

`data/gto-stability.json`（由 `scripts/gto-stability-probe.ts` **产出**，
不是手写）以**缓存键**为键存放证据。

```
有证据（runs ≥ 2 且菜单一致且漂移 ≤ 阈值）  → 允许升到 USABLE
没有证据                                   → 停在 LOW_CONVERGENCE
```

🔴 这是刻意的：**没有证据就不给高等级**。
`test/gtoCacheQuality.test.ts` 的 GTO-QUAL-04 断言「没有稳定性证据时必须是
`LOW_CONVERGENCE`」—— 这是本轮最重要的一条纪律测试。

## 2. 质量等级（用户 §八）

### 2.1 七档（有序）

| 等级 | 中文 | 含义 |
|---|---|---|
| `UNAVAILABLE` | 不可用 | 连数据都没拿到 |
| `FAILED` | 求解失败 | 拿到了请求但求解报错 |
| `LOW_CONVERGENCE` | 低收敛 | 拿到了策略，但收敛程度明显不足 |
| `APPROXIMATE` | 近似策略 | 模型本身是近似的（**GTOpen 翻前的天花板**） |
| `USABLE` | 可用 | 收敛达标 + 重复求解稳定 |
| `HIGH_CONFIDENCE` | 高置信 | 迭代充裕 + 达标 + 稳定 |
| `CROSS_CHECKED` | 已交叉验证 | 需要**第二个独立求解器**（本阶段**不可能**达到） |

### 2.2 判定规则（**先降级，后升级**）

```
1. 没有策略数据                     → UNAVAILABLE
2. 求解器报 state = error/failed    → FAILED
3. 模型近似                         → 天花板 APPROXIMATE（翻前**恒**命中这条）
4. 未达目标 / 迭代 < 20 / 有冻结座位 / 无稳定性证据 / 漂移 > 0.01
                                    → 降到 LOW_CONVERGENCE
5. 达标 + 证据齐全                   → USABLE
6. 达标 + 证据齐全 + 迭代 ≥ 40       → HIGH_CONFIDENCE
7. CROSS_CHECKED                    → **永不**由本函数产生
```

第 3 步是关键：**近似模型是所有等级的天花板**。
即使 gap 收敛到 0 且重复求解逐位一致，翻前结果也不会超过 `APPROXIMATE`。

### 2.3 「质量 ≠ API 成功」的落地

Phase 1 只有一个含混的「成功」：求解器回了数据就算成功。
现在拿到数据之后，**还要看六项事实**才能决定它能不能用：

| 输入 | 来源 | 为什么需要 |
|---|---|---|
| `brGapTotal` | 求解器自述 | 离均衡多远（**只在同一棵树内可比**） |
| `iterations` | 求解器自述 | 迭代 12 次与 600 次的「done」不是一回事 |
| `stopReason` | 求解器自述 | `target_reached` 与 `iteration_limit` 是两种结束 |
| `learningSeats` | 座位状态 | 冻结座位的 gap 是**出血**、永不收敛 |
| `approximation` | 我们自己的标记 | 近似模型封顶 |
| `stability` | **重复求解实测** | 漂移大的结果不可依赖 |

### 2.4 实测中各结果落在哪一档

| 场景 | 迭代 | gap | 停止原因 | 达标？ | 稳定性证据 | 等级 | 界面显示 |
|---|---:|---:|---|---|---|---|---|
| 4MAX / CO / RFI | 60 | 0.03412694 | `target_reached` | ✅（目标 0.05） | ✅ 2 次逐位一致 | `APPROXIMATE` | 近似策略 |
| 5MAX / HJ / RFI | 60 | 0.08084305 | `target_reached` | ✅（目标 0.1） | ✅ | `APPROXIMATE` | 近似策略 |
| 6MAX / UTG / RFI | 40 | 0.16526006 | `target_reached` | ✅（目标 0.2） | ✅ | `APPROXIMATE` | 近似策略 |
| 8MAX / UTG / RFI | 20 | 0.00417911 | `target_reached` | ✅（目标 0.05） | ✅ | `APPROXIMATE` | 近似策略 |
| 9MAX / UTG / RFI | 12 | 0.02102956 | `target_reached` | ✅（目标 0.05） | ✅ | `APPROXIMATE` | 近似策略 |
| 各桌型的 VS_OPEN 节点 | 同档 | 同档 | `target_reached` | ✅ | ❌ **未单独实测** | `LOW_CONVERGENCE` | 低收敛（黄色） |
| VS_3BET / VS_4BET | — | — | — | — | — | `UNAVAILABLE` | 未支持 |

**5 档桌人数的 RFI 全部落在 `APPROXIMATE`** —— 这是 GTOpen 翻前能达到的**最高**等级
（被近似延续模型封顶）。**没有一个是 `SOLVED` 或 `VERIFIED`**，这是设计使然。

⚠️ 最后第二行值得说明：VS_OPEN 节点与同档 RFI 用的是**同一棵树、同一套求解设置**，
因此收敛程度相同；等级低只是因为**我们没有单独为它们跑稳定性探针**。
这正是「没有证据就不给高分」的体现 —— 它不是「这些结果不好」，
而是「**我们还没有验证过它们稳定**」。

### 2.5 一个被实测抓出来的**规则冲突**及其修正

第一版的「迭代够不够」用的是**绝对阈值**（≥ 20 次）。它与自己的配置直接打架：

```text
9 人桌的迭代预算是 12 次（GTOPEN_SIZE_PROFILES）
9 人桌实测：12 次迭代、stop_reason = target_reached、gap 0.0210 < 目标 0.05
        ↓
求解器说「我到了」   ←→   我们的规则说「迭代太少，是早期快照」
        ↓
9 人桌永远卡在 LOW_CONVERGENCE，无论它是否真的收敛
```

**修正**：改成**按桌型标定**（`GTO_MIN_ITERATIONS_BY_TABLE_SIZE`），
判据是 **「求解器声称达标」或「跑满了该桌型的预算」** —— 二者取或。

- 「未达标」仍然是一条**独立**的 blocker，因此这不会让未收敛的结果蒙混过关；
- 反例有测试锁住：同样 12 次迭代但 `stop_reason = iteration_limit` ⇒ 仍判 LOW。

（测试：`GTO-QUAL-03` 与 `GTO-QUAL-03b`。）

### 2.6 另一个被实测抓出来的问题：**缓存里的冻结等级**

缓存条目里存的是**写入那一刻**的质量判定。而稳定性证据是离线探针**事后**产出的，
于是会出现自相矛盾：

```text
同一份数据：
  冷求解（有证据）→ APPROXIMATE
  读缓存          → LOW_CONVERGENCE   ← 用的是写入时那份
```

**修正**：读取缓存时按**当前证据重新评级**（`GtoSafeLookup.regradeEntry`）。

为什么这样改是安全的：`gradeGtoQuality` 是**纯函数**，输入只有
条目自身已存的元数据 + 当前的证据表；证据表由**离线实测**产出，
不是使用者能改的东西。因此重新评级只会在两个正确方向上动：
「证据补齐后如实上调」或「证据不足/漂移大时保持/降回 LOW」。

⚠️ 条目里那份**原始判定保留不动**（`entry.quality`），
因此「写入时判成什么」永远可查。测试：`GTO-CACHE-24`。

### 2.7 第三个问题：**陈旧条目必须被拒绝**

实测中还遇到一条由**旧代码**写入的条目：`solveMeta.targetGap = 0`（旧版没记目标），
而当前代码算出的键对应 `targetGap = 0.1`。它被当成「当前配置的结果」命中，
评级读到 `targetGap = 0` 就判成「未设收敛目标」⇒ 等级永远 LOW。

**修正**：在**解析阶段**拒绝 `solve` 与 `solveMeta` 自相矛盾的条目
（`parseCacheEntry` 现在比对 `targetGap` 与 `iterationsRequested`）。
表现是「未命中，重算」，而不是一个难以诊断的错误等级。
测试：`GTO-CACHE-22`（必须拒绝）与 `GTO-CACHE-23`（正常条目不受影响）。

## 3. 为什么**不能**用跨桌型固定 gap 阈值（用户 §九）

### 3.1 实测证据

| 配置 | 动作分支 | 树节点 | 10 次迭代后的 gap 之和 |
|---|---|---:|---:|
| 6MAX · `mult=[3]` `allin=false` | 2（Fold / Raise） | 1,272 | **0.015** |
| 6MAX · `mult=[3]` `allin=true` | 3（+ All-in） | 2,538 | **0.998** |
| 8MAX · `allin=false` | 2 | 12,362 | 0.025 |
| 8MAX · `allin=true` | 3 | 24,716 | **5.455** |

**同一张桌子，只是多了一条全下分支，gap 就差 60 倍。**
因此任何一条全局阈值（例如「gap < 0.01 就是高质量」）必然会在某类树上判错。

### 3.2 本项目的做法

| 做法 | 实现 |
|---|---|
| **收敛判定只在同一棵树内做** | `treeIdOf()` 产出树指纹；`GtoQualityEvidence.treeId` 是评级输入 |
| 跨树一律通过**事件**而非**数值**降级 | 未收敛 / 迭代过少 / 无证据 / 漂移 / 模型近似 |
| 拿不到足够证据时**选择更低的等级** | 缺证据 ⇒ `LOW_CONVERGENCE`；近似模型 ⇒ 封顶 `APPROXIMATE` |
| 每个桌型的收敛目标**按桌型标定**并留档 | `GTOPEN_TARGET_GAP_BY_TABLE_SIZE`，注释里写明这是**工程调参** |

### 3.3 每个桌型的收敛目标（及其性质）

| 桌人数 | 目标 gap | 依据 |
|---|---:|---|
| 4 | 0.05 | Phase 1 实测 60 次迭代达到 0.034 |
| 5 | 0.1 | 实测 60 次达到 0.081 |
| 6 | 0.2 | 实测 40 次达到 0.165 |
| 8 | 0.05 | 实测 20 次达到 0.004 |
| 9 | 0.05 | 实测 12 次达到 0.021 |

🔴 **这不是「gap < X 就是 GTO」**。它的唯一用途是让「是否达标」变成一个
**可判定**的信号：
- 达标 → 求解器以 `target_reached` **提前停下**（省时间，且我们知道到了哪）
- 未达标 → 以 `iteration_limit` 停下，我们**如实记成未收敛**

即使达标，翻前结果的质量等级上限**仍是 `APPROXIMATE`**。

### 3.4 ⚠️ 一个必须写进报告的读法陷阱

实测中 8 人桌的 gap（0.0042）**小于** 4 人桌（0.0341），
看起来像「8 人桌更精确」。**这是错的读法**：
4/5/6 人桌是 3 分支树（含全下），8/9 人桌是 2 分支树。
**不同的树 ⇒ gap 的定义不同 ⇒ 数字不可比。**
本报告**不**声称「8 人桌更收敛」。

## 4. 近似模型这条天花板（**一切标注的根源**）

`crates/solver/src/preflop/mod.rs` 文件头（逐字）：

> Solves the configured 2..9-player action tree with **modeled continuation
> payoffs, not a full postflop game**. … The 169-class chance model **ignores
> joint card removal**. … Multiway continuation is **showdown value, not
> learned postflop EV**. DCFR reports each seat's best-response gap against
> these model payoffs; **a small gap is not evidence of an accurate poker model
> or a Nash equilibrium**.

由此得到两条硬结论：

1. **即使 gap 收敛到 0，收敛的也是那个近似模型内部的均衡**，不是真实扑克。
   ⇒ 翻前结果上限 = `APPROXIMATE`。
2. **gap 小不是模型准确的证据**。
   ⇒ 不能把「gap 小」当作「结果可信」的论据。

### 4.1 数据可读性核对（**不是正确性证明**）

9MAX / BB vs BTN 开池（2 分支树，12 次迭代，gap 0.0210）：

```
AA   FOLD=0.1%   CALL@2.5=0.1%   RAISE@7.5=99.9%
AKs  FOLD=0.1%   CALL@2.5=0.1%   RAISE@7.5=99.8%
A5s  FOLD=0.1%   CALL@2.5=99.8%  RAISE@7.5=0.2%
22   FOLD=0.1%   CALL@2.5=99.9%  RAISE@7.5=0.1%
72o  FOLD=94.7%  CALL@2.5=5.3%   RAISE@7.5=0.1%
```

⚠️ 这里 `22` 与大对子被归入「几乎 100% 跟注」、`AA` 几乎 100% 3Bet ——
方向大体合理，但**低对子跟注 99.9% 并不是常见的 GTO 结论**。
可能的解释包括：近似延续模型对盲注防守的定价偏差、
迭代数过少（12 次）、以及多人权益模型（`coupled_deck_v1`）的近似。
**本报告不对此下结论**，只如实记录观察到的数字。

这正说明为什么必须保留「迭代数 / gap / 停止原因 / 是否达标」四项元数据：
没有它们，使用者无从判断一个看起来奇怪的数字是「模型的结论」还是「没算完」。

## 5. 与 Phase 1 的差异（本轮的实质改进）

| 项 | Phase 1 | Phase 1.1 |
|---|---|---|
| 状态字段 | 恒为字符串 `APPROXIMATE` | 由**七档质量等级**推导 |
| 收敛目标 | **没有**（`target_gap = 0`，跑满迭代数就停） | 按桌型标定，达标的求解器会**提前停下** |
| 迭代数是否显示 | 显示，但无判定作用 | 参与判定（< 20 直接降级） |
| 重复求解稳定性 | **未验证** | 实测（逐位一致），并写入 `data/gto-stability.json` |
| 是否有降级路径 | 只有「拿到 / 没拿到」 | 拿到之后还会按 6 项事实**降级** |
| 界面是否区分质量 | 只有「近似求解」一种横幅 | 低收敛用**不同颜色 + 不同措辞**，并显示 11 项来源/质量字段 |
| `CROSS_CHECKED` | 类型里存在但无实现 | 类型里存在，**评级函数保证永不产生**，并有测试 |
