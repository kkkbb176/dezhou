## B. 原始牌局输入核对

### B.1 关键契约发现：`seatStacksBB` 是「**开手时**筹码」

`src/app/manualInput/reconstruct.ts:274-295`：

```ts
const stackChipsOf = (position) => { ... return Math.round(explicit * bigBlindChips); };
const seeds = participating.map((position) => ({ ..., startingStack: stackChipsOf(position), ... }));
state = createGame({ config: {...}, players: seeds, ... });
```

`seatStacksBB[position]` 被直接当作 `createGame` 的 **`startingStack`**（盲注尚未投入）。
因此题目给的「Hero 当前剩余 94BB / BB 当前剩余 83.5BB」是**决策时点余额**，不是开手筹码。
两者换算（开手均 100BB）：Hero `100 − 2.5 − 3.5 = 94BB`；BB `100 − 2.5 − 14 = 83.5BB`。
⇒ 正确输入是 `effectiveStackBB: 100`（不填 `seatStacksBB`），实测引擎回算 `我的剩余筹码 94.0BB`、`有效筹码 83.5BB`，与题目完全一致。

**把 94/83.5 填进 `seatStacksBB` 会被当成开手筹码并再次扣减**（实测得到 88.0BB / 67.0BB）。这是接口语义陷阱，不是引擎算错。

### B.2 另一处契约：`CALL` 用增量，`RAISE` 用本街累计

实测：`BB CALL amountBB: 2.5` 被拒（`ISSUE.CALL_AMOUNT_ILLEGAL`），`1.5` 通过（BB 已投 1BB）。
与 `src/app/table/table.types.ts:330-333` 的说明一致（`BET/RAISE/ALL_IN` = 本街总额；`CALL` = 本次投入）。

## C. 资金流与合法加注金额（独立复算）

独立复算脚本 `kq-flop-raise-42bb-independent.mjs`，口径与 `contextBuilder.ts:4193-4220` 逐式对应：
`heroAdd = raiseTo − heroStreetCommitted`；`villainAdd = min(raiseTo − villainStreetCommitted, villainRemaining)`；
`heroContestedAdd = min(heroAdd, villainStreetTotalAfterCall − heroStreetCommitted)`；`finalPot = currentPot + heroContestedAdd + villainAdd`。

| 本街累计 | heroAdd | villainAddRaw | villainAdd | contested | finalPot | 未匹配退回 |
|---:|---:|---:|---:|---:|---:|---:|
| 24.5BB | 2100 | 1050 | 1050 | 2100 | 5450 | 0 |
| 26.25BB | 2275 | 1225 | 1225 | 2275 | 5800 | 0 |
| 31.5BB | 2800 | 1750 | 1750 | 2800 | 6850 | 0 |
| **42BB** | **3850** | 2800 | 2800 | **3850** | **8950** | **0** |
| 52.5BB | 4900 | 3850 | 3850 | 4900 | 11050 | 0 |
| 63BB | 5950 | 4900 | 4900 | 5950 | 13150 | 0 |
| 84BB | 8050 | 7000 | 7000 | 8050 | 17350 | 0 |
| 97.5BB（全下） | 9400 | 8350 | **8350**（被其剩余封顶） | 9400 | 20050 | 0 |

（单位：筹码，1BB = 100）

结论：
- **无重复扣除**：本次再投入用 `raiseTo − 350`，已投入的 3.5BB 未被二次扣减。42BB 时 `heroAdd = 3850 = 38.5BB`，与题目「本次再投入 38.5BB」一致。
- **无未匹配筹码进入底池**：全下档 villain 只能补到 8350（其全部剩余），`uncalledReturn = 0`，终池 20050 恰为双方本街总额之和 + 死钱 1150。
- **无重复计入**：终池口径为 `currentPot + contested + villainAdd`，弃牌分支返回完整 `currentPot`，两者不叠加。

## D. 42BB 的准确生成路径

**不是 EV 最大化选尺寸，而是「启发式目标 → 吸附最近档」。** 完整路径：

1. **`buildSizeGrid(legal, pot, 'RAISE')`** —— `src/app/manualInput/legalActions.ts:252`
   - `toCall = legal.currentBet − streetAlready = 1400 − 350 = 1050`
   - `RAISE_MULTIPLES = [2, 2.5, 3, 4, 5, 6, 8]`（`:276`）⇒ 候选 `2100 / 2625 / 3150 / 4200 / 5250 / 6300 / 8400`
   - 无条件并入 `minTo = 2450`、`maxTo = 9750`（`:319`）
   - `2100 < minTo` ⇒ 丢弃（`:325-326`）
   - ⇒ **网格 = [2450, 2625, 3150, 4200, 5250, 6300, 8400, 9750]**（8 档，与运行实测一致）
2. **启发式目标尺寸** —— `src/app/manualInput/contextBuilder.ts:4152`
   ```ts
   const desiredTo = currentPot + 2 * heroCallCost;   // 2300 + 2×1050 = 4400 = 44BB
   ```
   （`contextBuilder.ts:4144` 注释声明决策层用**同一**底池基准与同一目标式）
3. **吸附最近合法档** —— `contextBuilder.ts:4153-4155`
   `closestSizeTo(grid, 4400)`：`|4400−4200| = 200` vs `|4400−5250| = 850` ⇒ **4200 = 42BB**
4. **仅对此尺寸算一次 EV** —— `contextBuilder.ts:4313-4325` 调 `raiseEVOf`（`src/app/manualInput/raiseResponse.ts:129`）
5. 与 CALL 的 `PROXY_EV` 在同一零点比较（`decisionSource` 自报 `SUPPORTED_ACTION_PRIORITY`，优先级 4）

### D.1 逐条回答

| # | 问题 | 回答 |
|---|---|---|
| 1 | 为什么选 42BB | 因为 `pot + 2×callCost = 44BB` 距 42BB 档最近（差 200 筹码） |

### E.1 选中尺寸的响应分解（引擎自报，`allReasonsZh`）

```text
加注：42.0BB。面对加注的响应模型 EV = 1948.14 筹码 vs 跟注 1644.52 筹码（同一零点 = 弃牌 0）
⇒ 依据来源 = SUPPORTED_ACTION_PRIORITY
｜他面对这次加注：弃 88.0% / 跟 7.7% / 再加注 4.3%（价格 0.3128，模型 PUBLIC_BAND_RAISE_RESPONSE_V1）
```

- **概率和为 1**：`0.880 + 0.077 + 0.043 = 1.0000` ✅
- **再加注分支**：`reRaiseLikelihood = 4.3% > 0`，引擎按 `max(−heroContestedAdd, EqVsReraise × 跟注后终池 − heroContestedAdd − 我需再投)` 计算（`contextBuilder.ts:4303-4308`）；拿不到则退回下界 `−heroContestedAdd` 并如实标注 `LOWER_BOUND_NOT_IMPLEMENTED`

- **后续街道**：非全下分支按**摊牌终止近似**计入（未模拟转牌/河牌行动），引擎明确声明该 EV 偏低且**不构成严格下界**

## H. 独立权益与 EV 复算

| 复算项 | 引擎值 | 独立复算 | 判定 |
|---|---|---|---|
| CALL EV = EqVsBetRange × winnable − callCost | 1644.52 | `0.8043 × 3350 − 1050 = 1644.41` | ✅（差 0.11 = 权益显示舍入） |
| 底池赔率 = callCost / (pot + callCost) | 31.3% | `1050 / 3350 = 31.34%` | ✅ |
| RAISE EV 三分支公式 | 1948.14 | 反解条件权益 53.5%–56.0%，落在独立可行区间内 | ✅ 自洽 |
| `P(弃)+P(跟)+P(再加注)` | — | `0.880+0.077+0.043 = 1.0000` | ✅ |
| 容差带 = 5% × winnable | ±167.50 | `0.05 × 3350 = 167.50` | ✅ |
| RAISE 相对 CALL 的优势 | 303.62 | `1948.14 − 1644.52 = 303.62 > 167.50` | ✅ 超出容差带 |

**结论：EV 公式与资金流口径自洽，未发现把牌力评分当作权益/EV 的情况**
（响应中 `强度 0.62` 仅出现在「相对牌力角色」字段，与权益字段分离）。

## J. 已确认缺陷、模型限制与尚未证实的问题

### J.1 已确认缺陷（披露层，全部可复现）

| ID | 缺陷 | 证据 | 严重度 |
|---|---|---|---|
| **D1** | **同一响应内三处对「加注 EV 是否存在」互相矛盾** | ① `debug.candidates`：`加注 42.0BB → EV "—（依赖弃牌率，本项目无可信估计）"`；② `debug.decisionSource`：`证据 RAISE｜MODEL_EV｜EV 1948.14`（正是选它的依据）；③ `debug.mathDominance`：「下注/加注的 EV 依赖对手弃牌率，本项目无可信估计，**不在此比较之内**」 | 高 |
| **D2** | **决策边际自述「未比较加注」，而同一响应的来源说明称「跨动作比较已做」** | `decisionMargin`：「明显优于弃牌（**仅**已证明 CALL > FOLD，**未比较加注**）」 vs `decisionSource.来源说明`：「RAISE vs CALL：各自模型的 EV 差 303.63 筹码 ⇒ 跨动作比较**已做**」 | 高 |
| **D3** | `debug.player` 标签字段与实际采用的画像矛盾 | `标签: UNKNOWN` 与 `说明: 无实测数据，采用用户手选画像「AGGRESSIVE」` 同时出现 | 中 |
| **D4** | 「本次进入模型 = 无（该玩家尚无模型支持的统计项）」**不实**，且 `flopCheckRaise` 无输入通道 | 实测 VPIP/PFR 使 RAISE EV 由 2038.26 变为 2037.45、权益由 82.02% 变 82.36%；而 `flopCheckRaise` 取 4% 与 25% 时权益与 EV **逐位相同** | 中高 |
| **D5** | 决策边际以 **CALL 的 EV** 作为判据描述一个 **RAISE** 决策 | 变体 4：`边际判据: 真实跟注 EV 1578.35`，`边际说明 ⇒ CLEAR_CALL_OVER_FOLD`，但最终动作是 RAISE（EV 1669.29） | 中 |

> D1/D2 属于同一根因：`candidates` 列表与 `mathDominance` 仍按「翻后加注 EV 不可得」的旧口径渲染，
> 而决策层已经改走「单尺寸响应模型 EV」，两条渲染路径未同步。

### J.2 模型限制（引擎已如实披露，不计为缺陷）

1. 加注 EV 只对**一个**尺寸计算 ⇒ 尺寸选择非 EV 驱动。
2. 非全下加注按**摊牌终止近似**计入，未模拟转牌/河牌行动 ⇒ 该 EV 偏低。
3. Hero 面对非全下再加注时的 **4-Bet 未实现**。
4. 无 **Rake Engine** ⇒ 全部 EV 未计抽水。
5. 尺寸菜单为固定倍数轴 ⇒ **35BB 等合法尺寸不可选**。
6. 翻后**无求解器范围**（`NO_SCENARIO`），全部使用启发式先验 + 行动似然更新。
7. 响应概率为 `PUBLIC_BAND_RAISE_RESPONSE_V1` **结构性先验，未经统计校准**。

### J.3 尚未证实的问题

1. **42BB 是否为 EV 最优尺寸**——无法评估（7 档无 EV）。
2. **抽水对 42BB vs CALL 排序的影响**——无抽水模型，无法量化。
3. **`flopCheckRaise` 缺失对结论的实际影响**——已确认该统计不进模型，但其应有权重未被定义，故无法量化"若有该通道结论会如何变化"。
4. 引擎隐含的 `callContinueEntries` 具体构成未对外暴露 ⇒ 只能通过反解区间（53.5%–56.0%）间接约束，**不能逐组合核对**。

## K. 当前建议是否具有充分的数学证据支持

| 维度 | 评估 |
|---|---|
| 资金流正确性 | **充分**。8 档独立复算一致，无重复扣除/未匹配计入 |
| 权益正确性 | **充分**。引擎 `EXACT` 枚举与独立枚举器互证，无系统偏差 |
| 概率自洽性 | **充分**。三分支概率和为 1.0000 |
| 动作依据 | **部分充分**。RAISE(1948.14) > CALL(1644.52) 超出容差带 167.50，证据等级 `MODEL_EV`、置信度 0.70 |
| 尺寸依据 | **不充分**。42BB 由 `pot + 2×callCost` 启发式吸附得出，**未经任何尺寸间 EV 比较** |
| 对手画像依据 | **不充分**。题目画像未绑定；实测统计几乎不进决策；关键统计 `flopCheckRaise` 无通道 |
| 披露一致性 | **不充分**。存在 D1/D2/D3/D4/D5 五项自相矛盾 |

**总评：`RAISE 42BB` 这个「加注」的方向性结论有可复算的数学支撑（在引擎已建模的范围内），
但「42BB」这个具体尺寸没有 EV 证据，且结论对画像不敏感，而披露层存在多处自相矛盾。
因此本建议当前**不具备完整充分的数学证据**——属于「方向可复算、尺寸未证明、披露不可信」。**

## L. 后续修复优先级及最小修改建议

| 优先级 | 缺陷 | 最小修改建议 | 风险 |
|---|---|---|---|
| **P0** | D1 候选表与决策来源对同一尺寸的 EV 说法矛盾 | 让 `candidates[]` 渲染读取决策层已算出的**该尺寸** `MODEL_EV`（含其证据类型与置信度），无 EV 的档位保持「未计算」并注明原因 | 仅改渲染，不动策略 |

| **P2** | D3 标签字段矛盾 | `标签` 应报实际生效来源（`USER_ARCHETYPE` / `OBSERVED_HAND_HISTORY`），而非恒报 `UNKNOWN` | 仅改渲染 |
