### 5.2 BR gap 的定义、单位与归一化（查明）

- **来源**：求解器 `GET /api/preflop/status` 的 `gap_total` 与逐座位 `gaps[]`；provider 原样搬运，**不解释、不换算**。
- **含义**：每个座位的 **best-response gap**（DCFR 迭代中「偏离当前策略能多赚多少」的度量），9 个座位**求和**得 `gap_total`。
- **单位**：与座位 EV 同单位的**收益量**（`evs` 与 `gaps` 同量纲）。实测本场景 `gap_total=0.0210` 而座位 EV 在 `−0.44 ~ +0.19` 区间 ⇒ gap 相对量级很小。
- **归一化**：**本项目不做归一化**，原样使用。因此 gap **只在同一棵树内可比** —— `treeId` 相同的两份结果才能比。
  这也是 9MAX 用 `targetGap=0.05`、6MAX 用 `0.2`、4MAX 用 `0.05` 的原因（按树标定，不是全局常数）。
- **`targetGap` 来源**：**求解侧配置**（`profileForTableSize(tableSize).targetGap`），不是本项目的判断。
  本项目只做「`gap_total` 是否低于求解器自己设的目标」这一个比较。

### 5.3 缓存必须匹配实际求解条件

缓存键 = 场景哈希 + 求解设置指纹，实测覆盖（逐维扰动验证）：

| 维度 | 是否进键 |
|---|---|
| 桌人数（9 / 6 / …） | ✅ 不同 |
| 有效筹码（100 / 40 / 1000 / 1000000BB） | ✅ 不同 |
| 位置（UTG / UTG1 / …） | ✅ 不同 |
| 场景类型（RFI / VS_OPEN） | ✅ 不同 |
| 盲注结构 / 前注 / 座位定义 | ✅ 进 `solveKeyParts` |
| 下注树（开池尺寸 / 加注倍数 / 上限 / 跛入 / **是否含全下**） | ✅ 进 solve 指纹 |
| 求解器版本（engineCommit） | ✅ 进 solve 指纹 |
| RFI 的 `openSizeBB` | ❌ **不进键**（RFI 前序动作恒为空）⇒ 由闸② `solveSettingsMatch` 单独挡 |

**结论**：缓存**不能**跨桌人数/筹码/位置复用；同一 9MAX 场景的 `g0d4f06d8` 与 6MAX 的 `gb2c2da23` 是两把不同的键，实测互不命中。

### 6.3 「1225 组合」的统计含义（任务明确要求查明）

**结论：1225 不是「有效范围宽度」，它等于 C(50,2)，即「已知 Hero 两张牌后的全部组合」。**

```text
组合宇宙（去掉 A♠A♥）= 1225 = C(50,2)
正权重组合数（rawWeight > 0）= 1225      ← 与宇宙**相等**
Σp = 1.0000000000
有效组合数 1/Σp² = 94.06                 ← 真正的等效宽度
归一化熵 = 0.6565（0..1）
前 10 个组合占比 = 11.4%
```

原因：求解器在**全部 169 个牌型类**上都留了非零 RAISE 频率
（正权重类 169/169，其中 **141 类权重 < 0.01、132 类 < 0.001**），
展开后每一类都贡献组合 ⇒ 正权重数必然等于全部组合。

**权重口径核对**（这是「169 类 → 具体组合」的转换规则）：

| 环节 | 规则 | 实测证据 |
|---|---|---|
| 动作合并 | 取该节点上 `RAISE` + `ALL_IN` 的频率之和（本场景无 `ALL_IN`，等价于 RAISE 频率），夹到 `[0,1]` | `weightsFromRange` |
| 牌型对齐 | **按牌名**（`hand.hand`），绝不按序号 —— 项目里两套 169 类顺序只有 5/169 相同 | 代码纪律 |
| 类 → 组合 | 每个组合取**其所在类**的权重，再对全部保留组合归一化 | 见下 |
| 最大权重 | 0.999231（`AA`/`KK`/`QQ`/`66`… 的 RAISE 频率 = 0.9992308） | 载荷逐条核对 |
| 最小正权重 | 0.000769（`22`/`76s`/`72o` 的 RAISE 频率 = 0.0007692） | 同上 |
| **权重总量** | **Σw = 19.115796**（169 类权重之和） | 实测 |
| **加权组合数** | Σ(**该类组合数** × 类权重) = **121.094**（对子 6 / 同花 4 / 不同花 12） | 实测（我用 `6×Σw` 粗算得 114.7，那是错的：只有对子是 6 个组合） |

所以「入池范围宽度」的正确读法是 **94.1 个组合（1/Σp² 等效）/ 121.1 个组合（加权）**，
而不是 1225。**1225 不携带范围信息**。
（两者不同是正常的：`1/Σp²` 对**高权重**的组合更敏感，加权和则按类计数。）

**已知牌冲突的移除与归一化**（实测）：

```text
死牌 = A♠(idx 12) + A♥(idx 25)
宇宙 = 1225（从 1326 中移除所有含 A♠ 或 A♥ 的组合）
移除后重新归一化 ⇒ Σp = 1.0000000000（实测）
```

## 八、`maxRaises` 单独判断

**结论：与本轮选定的 9MAX 场景无关，不需要改，留作后续任务。**

| 问题 | 答案 |
|---|---|
| 本轮场景受它阻断吗？ | **不受**。本手 `raiseCount = 1`（只有 UTG 开池一次），而 `maxRaises` 只影响 `raiseCount ≠ 1` 的节点。实测本场景**已成功求解并落盘**（`target_reached`） |
| 它在场景构造里的语义 | `solveKeyParts().maxRaises` 进 solve 指纹；树按「最多几次加注」建。生产=2 ⇒ 树里**没有** 3Bet 之后的节点 |
| 求解器里的语义 | 能力表实测：`VS_OPEN` 代码已实现（`heroAlreadyActed` 形态），但节点可达性要求 `max_raises ≥ 3`；生产配置 2 ⇒ **不可达** |

## 十二、大白话结论

> **现在这个 9 人桌场景能不能真正用上？**
>
> **能，而且是真用上了。** 9MAX / 100BB / 枪口位开池 2.5BB 这个局面，
> 求解器**真的算了一遍**（3 分 1 秒、12 次迭代、gap 0.021 达标），
> 结果**真的存进了缓存**，页面**真的**把枪口位的范围从「猜的」换成了「算的」——
> 我核对过：Hero 对对手范围的权益从 83.0% 变成 84.4%，跟注 EV 从 306.36 变成 314.10，
> 范围可信度从 0.30 提到 0.55，页面上也照实写了「范围来自求解器 + 已通过准入 + 这只是近似模型」。
>
> **首次需要多久？** 你第一次遇到这个局面，**0.5 秒**就出结果 ——
> 但那一次用的是启发式范围，同时后台开始算。**3 分钟后**它才算完并存好。
> 想让它算，得保证 GTO 求解器开着（默认 `127.0.0.1:3737`）。
>
> **再次需要多久？** **0.4 秒**，而且这次真的是求解器范围。重启服务也还是 0.4 秒
> （从磁盘读）。我已经实测过「杀掉进程→重启→还是命中」。
>
> **不支持或算不完时会怎样？** 它会**明说**，绝不假装：
> - 换个人开池（比如 HJ/CO/BTN 开池、或开到 3BB）→ 直接告诉你「这个局面算不了，**等也不会变**」；
> - 还在后台算 → 页面上写「⏳ 正在后台计算，本次用启发式范围」，并说明下次会自动变；
> - 算出来但不达标 → **不采用**，回落启发式，并把拒绝原因写出来；
> - 求解器没开 → 明确报「求解器不可用」。
>
> **三件必须知道的事**：
> 1. 这个范围是**近似模型**算的（不是完整 GTO），而且**没有全下分支** ——
>    求解器的动作菜单只有「弃牌 / 加注 2.5BB」。A♠A♥ 建议你全下，那是**我们自己的决策模型**给的，不是求解器说的。

> 3. 它算的是「**对手的范围**」，不是「整手牌的最优解」——
>    行动建议始终由现有决策模型给出。
