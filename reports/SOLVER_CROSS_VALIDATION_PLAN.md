## 0. 结论先行：判定协议

```
两份结果出现差异
  ↓
① 先比 EV，不比频率                    ← 核心原则
  ↓
② 结构性审查（坐标轴 / 玩家槽位 / 字符串规范化）   ← 先排除包装层
  ↓
③ EV gap 小  →  标记「策略混频不唯一」，**不是 Bug**
   EV gap 大 或 纯策略方向相反  →  CRITICAL REVIEW
```

**三条依据**：

1. **DCFR-SOLVER**：不同 CFR 实现每手频率差 12–15%，但 499 手中 241 手的 EV 差 < 0.1 筹码；
   **纯策略（100% 下注或 100% 过牌）在所有被测求解器间 100% 一致**。
2. **poker_solver**：一处 33 个百分点的差异最终归因为「同一无差异流形上的不同点」，
   仲裁结论「NOT A BUG」。

## 1. 为什么不能直接比频率

### 1.1 多重纳什均衡是数学事实，不是近似误差

当一手牌在两个动作间**无差异**（EV 差 ≈ 0）时，**任何混合比例都是有效的纳什策略**。
不同 CFR 实现（不同的后悔折扣、不同的遍历顺序、不同的浮点累积顺序）
会收敛到**不同的有效均衡**。

**推论**：
- 「A 给 47% 下注、B 给 59% 下注」**不能**判其中一个是 Bug
- **纯策略的一致性**才是可判定的信号（若连纯策略都不一致，就无法用多重均衡解释）

### 1.2 聚合器 ≠ 真纳什（必须记录求解的是哪个对象）

poker_solver 精确区分了两个名字相似的路径：

| 路径 | 它实际求解的对象 |
|---|---|
| 聚合器 | 每个（我方组合, 对方组合）的**完全信息 1v1 纳什**，再按组合数池化 |
| 向量形式 | 我方范围 vs 对方范围的**联合不完全信息**纳什 |

> 聚合器「is **not** Nash for the range」—— 每个子博弈都能看到对方确切底牌，
> 因此**永远不会**做范围驱动的诈唬抓取或极化下注。
> 其输出看起来像混合策略，实际是「打败了多少比例的代表」的**直方图**。

**要求**：任何求解器结果入库时，必须记录它求解的是**哪个数学对象**。
**禁止**用聚合结果回答范围级问题（诈唬抓取 / 极化下注 / 诱导策略）。

## 3. 比较维度（规范第 31 节）

**明确禁止**：比较单一混频百分比。

| 维度 | 比较方法 | 判定 |
|---|---|---|
| **EV** | 逐动作 EV 的绝对差（筹码） | **主判据** |
| **Dominant action** | 最高 EV 动作是否相同 | 不同 → 记录 |
| **Pure action** | 纯策略（100%）的手牌集合是否一致 | **方向相反 → CRITICAL** |
| **Range direction** | 范围整体是变宽还是变窄 | 方向相反 → CRITICAL |
| **Equity** | 权益逐位或误差在可解释范围内 | 超出 → CRITICAL |
| **Exploitability** | 各自报告的可利用度 | 任一显著偏高 → 该实现有问题 |

### 3.1 EV gap 的阈值（**必须自行标定**）

> ⚠️ DCFR 使用「0.1 筹码」作为「无差异」的判据，但那是**它的**场景标定。
> 本项目**不得直接照搬**，必须用自己的场景标定（不同底池尺度下绝对筹码差不可比）。

建议做法：用 **EV gap / 底池** 的**相对**量作为阈值，并记录标定过程。

## 4. 四层验收门（借鉴 poker_solver）

poker_solver 的 v1.5 验收测试从「严格逐格相等」改造为：

```
① 结构性审查        ← 代码级：迭代循环、折扣、后悔匹配、平均策略
② 浅筹码严格逐格    ← 此时树小，应当可以完全一致
③ 深筹码 max-L1 ≤ ε ← 承认深筹码的均衡歧义，改用聚合距离
④ top-action ≥ 60%  ← 承认混频不唯一，但主要动作应当一致
```

**本项目采纳这套结构**，但 ε 与 60% 这两个数值**必须自行标定**，不得照搬。

## 5. 必须排除的测试侧瑕疵（poker_solver 的真实教训）

一处 **22–42 个百分点**的验收信号，最终被证实是**三个测试侧编码瑕疵**：

| # | 瑕疵 | 具体形式 |
|---|---|---|
| 1 | **动作轴列序** | 对方输出 `[c, f, r_low, r_med, r_jam]`；本实现按动作 id 排序输出 `[f, c, r_low, r_med, A]` → 位置索引错位 |
| 2 | **范围与玩家槽位反转** | 对方的 P0 在河牌先行动，本引擎是 P1 |
| 3 | **手牌字符串花色序** | `cdhs` vs `shdc` |

**→ 本项目要求**：任何差分测试在开始前必须**先锁定并显式记录**：

| 约定 | 必须固定 |
|---|---|
| 动作轴顺序 | 升序？按 id？按语义？ |
| 玩家槽位 | 谁先行动？ |
| 花色顺序 | 统一为 `s h d c` 还是 `c d h s`？ |
| 范围字符串语法 | 本项目使用 169 类语法，需转换 |
| 单位 | 筹码绝对额 vs 大盲 vs 底池比例 |
| 舍入 | 谁在什么时候舍入 |

## 9. 诚实结论

> **本方案的当前价值不是「可以开始验证了」，而是「记录了什么情况下不能下结论」。**

三个可立即使用的产出：

1. **判定协议**：EV 优先于频率；纯策略一致是可判定的必要条件。
2. **测试侧约定清单**：避免重演 22–42 个百分点的假信号。
3. **执行前置条件清单**：明确当前为「仅研究」，防止把方案误当成能力。

三个**不能**做的事：

1. 不能在没有第二个 Solver 的情况下做交叉验证。
2. 不能用聚合器输出回答范围级问题。
3. 不能把深筹码求解结果用于实时决策（算力不兼容）。
